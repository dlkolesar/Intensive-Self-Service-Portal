API Documentation

Getting Started

The Segment Support Self Service API's are separated based on system. Each Segment Support system has(or will have) its own API, e.g., a SCOM API and a separate Active Directory API, and yet another API for Windows Patching. The URLs for each API will take the follwoing general format:

https://hostServer/system/version/resource[/id]...

where

  • hostServer is the FQDN of the server hosting the API, typically, this will be api.intensive.int
  • system a short identifier for the Segment Support system the API talks to. e.g., scom, ad, av, etc...
  • version will intially be v1. If/when breaking changes are introduced, the version number will be incremented by one
  • resource identifies what object(s) you want to work with. This will always be a noun and be pluralized(users, domains, rules, ...).
  • id optionally, identifies a single, specific instance of a resource, i.e., a specific server, or a user account

In some cases, additional, resource and resource/id's may be added to the URL to get additional "sub" resources. For instance, the URL

https://api.intensive.int/ad/v1/domains/intensive/groups/devs/members

will go to the Active Diretory API(ad), connect to the intensive domain, get the group named devs and return the membership list.

Generally, URLs that end with a resource name will accept one or more search/filter parameters in the querystring and return the results in an apiCollection object(see below). URLs that end with and id will generally return a JSON-object representing that specific resource.

Return Codes and Errors

Standard HTTP error codes are returned by the APIs

200 OK The Request was successful. A JSON data object will be in the body of the Response. Be aware that the returned object may be an empty array

204 No Content The Request was successful, however no data is returned. This is common for PUT and DELETE requests

401 UnAuthorized The X-Auth-Token header was not present or the token provided in the header is invalid or expired

403 Forbidden The user associated with the token in the X-Auth-Token header is not allowed to perform the request

404 Not Found The resource identified by the URL was not found

500 Internal Server Error An unexpected error occurred in the API. An ApiError object is returned, which contains information about the error

Api Collections

Many endpoints within the Segment Support API's are used to search for resources that match a set of criteria, such as

https:/api.intensive.int/ad/v1/domains/intensive/users?filter=(employeeid=rs1234)

which will return all AD user accounts that have an employeeid of 'rs1234'".

Rather than return the actual data object(s) that match the criteria, an apiCollection object is returned, which contains an array of 0 or more URL's for each matching object (along with a count of how many urls are in the array), rather than an array of the actual objects.

Returning the matching resource URLs, instead of the actual object representation(s) provides a couple of advantages to your application:

  • You know exactly how many items are in the result set so you can decide how to handle paging operations, or IF you even want to fetch the objects
  • Knowing the size of the result set gives you the ability to show a progress bar/dial as you fetch the matching resource objects.
  • Your app can become more responsive; Depending on how large the objects are, and how many are being returned, it is far quicker to transmit a set of urls than a set of object representations. The larger the object, the larger the savings will be

API endpoints that return an apiCollection object will return an empty object if there are no matches and the HTTP return code will be 200, not 404

{{ '{' }} "count": 0, "resources": [] {{ '}' }}
Authentication and Authorization

All POST, PUT and DELETE HTTP methods, and even some GET operations, will require a valid Rackspace Identity token, which should be presented in an X-Auth-Token header of the request.

An Identity token can be generated by the Rackspace Identity API, https://identity-internal.api.rackspacecloud.com/v2.0/tokens and passing a payload similar to this:

{{ '{' }} "auth": {{ '{' }} "RAX-AUTH:domain": {{ '{' }} "name": "Rackspace" {{ '}' }}, "passwordCredentials": {{ '{' }} "username": "SSO", "password": "SSOPASS" {{ '}' }} {{ '}' }} {{ '}' }}

Change SSO and SSOPASS to your Rackspace SSO userid and password.

Many of the Active Directory API endpoints prevent you from altering any user accounts or groups that are not "yours". Ownership of a user account is assigned by populating the EmployeeId property of the AD user object with your Rackspace employee id. In this manner, one or more service accounts could be managed via the API, but only by the "owner" of the service account as indicated by the employeeid attribute.

The API will compare the EmployeeId attribute of the AD user account you are attempting to modify with the EmployeeId attribute of the SSO associated with the Identity token that is present in the required X-Auth-Token header. If the two match, the change is allowed, otherwise, a 404 FORBIDDEN error is returned.

NOTE: the EmployeeId attribute cannot be changed via the AD API.
